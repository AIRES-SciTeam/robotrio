# Скрипты физического AiNex

Для следования линии нужен один файл `line_follow.py`; он читает камеру и
выбирает одно из пяти штатных движений через `MotionManager.run_action`.
Без `--execute` работает только наблюдение. Голова сохраняет текущее положение.
Штатные драйверы HiWonder, камера, ROS Noetic и ActionGroups должны быть установлены.
Исходные ActionGroups получены напрямую с робота и подтверждены пользователем;
повторная проверка диапазонов для их штатного вызова не требуется.

`tag_grab.py` — отдельный сценарий подхода к кубу; текущая версия останавливается
после измерения в приседе. Прежний сценарий двух захватов был проверен пользователем.
Корневые `tag_grab.py` и `line_follow.py` — символические ссылки на исходники в этой папке.
[Локальная симуляция](../simulation/README.md) запускается отдельно от физического робота.
[Карта сервоприводов и ID AprilTag](SERVOS_RU.md) содержит назначения всех 24
приводов и предложение по модулю позиционирования и установки блока в паз.
[Лист проверки сервоприводов](SERVO_CHECKLIST_RU.md) содержит команды для
физического робота и таблицы для записи измерений перед разработкой захвата.

### Отслеживание AprilTag головой

`tag_track.py` центрирует выбранный AprilTag только головой: ID 23 — поворот,
ID 24 — наклон. Подтверждённые пользователем диапазоны pulse: **300–700**
для поворота и **350–650** для наклона. Скрипт не вызывает ActionGroups.
Остановите другие сценарии управления головой; драйверы, камера и штатный
AprilTag-детектор должны быть уже запущены. Детектор HiWonder должен публиковать
`corners` в `/tag_detections`, а `/camera/camera_info` — размеры его изображения.

Скопируйте `robot/tag_track.py` на робота в каталог сценариев внутри существующего
контейнера `ainex`, например `/home/ubuntu/robotrio/`. Запуск в ROS-окружении
контейнера из этого каталога:

```bash
# Только наблюдение, без создания MotionManager и команд сервоприводам:
python3 tag_track.py --id 0

# Отслеживание с подтверждёнными диапазонами по умолчанию:
python3 tag_track.py --id 0 --execute

# Более узкие рабочие диапазоны и меньший шаг коррекции:
python3 tag_track.py --id 1 --execute --pan-range 400 600 --tilt-range 400 600 --max-step 4
```

Перед первой командой скрипт читает фактические положения ID 23–24. Если любое
из них вне выбранного диапазона или чтение не удалось, он завершится без движения.
Начальный и конечный поворот к центру не выполняются. Центр изображения берётся
из `CameraInfo`; `--topic` и `--camera-info` позволяют выбрать другие топики.
В кадре должен быть ровно один экземпляр выбранного ID; bundle и дубликаты
этого ID не используются. Другие ID не мешают отслеживанию.

По умолчанию зона покоя — ±15 пикселей по каждой оси (`--deadband`), коэффициент
коррекции — 0,05 pulse/пиксель (`--gain`), предел одного шага — 8 pulse на ось
(`--max-step`), длительность движения — 150 мс (`--move-ms`), пауза после него —
0,05 с (`--settle`). Следующая коррекция использует только новый кадр, снятый
после движения и паузы. Старые, повторные и нулевые timestamp отбрасываются;
максимальный возраст изображения — 0,5 с (`--max-age`).

При достижении границы диапазона команда дальше неё не отправляется.
При потере метки новые движения прекращаются, при повторном обнаружении
отслеживание продолжается. Ctrl+C завершает скрипт без возврата головы;
уже отправленная короткая команда может закончить движение.
По горизонтали учтено подтверждённое наблюдение из `tag_grab.py`: больший X
находится левее; увеличение pulse ID 23 поворачивает голову влево. По вертикали
знак соответствует штатному трекеру HiWonder. Для противоположного направления
координат доступны `--invert-pan` и `--invert-tilt`.
Журнал показывает `OBSERVE`, `TRACK`, `CENTERED` или `LIMIT_OR_SMALL_STEP`.
После начального чтения pan/tilt в журнале обозначают последние команды,
а не измеренную позу. Новый сценарий физически ещё не проверен.

### Захват по AprilTag: текущие ограничения

`tag_grab.py` пока использует центр метки в пикселях. Последовательность:
подход по прежним порогам стойки → два `forward_one_step` → штатное подсаживание
→ серия новых измерений. После подшагов видимость метки не требуется:
в этой стойке она ожидаемо выходит из кадра, а измерить её можно после приседа.
При `--final-steps 0` измерение также выполняется только после подсаживания.

**Сейчас `--execute` останавливается в приседе с ошибкой `CALIBRATION_REQUIRED`
после записи измерений; окончательный захват не выполняется.** Подтверждённого
критерия положения блока после приседа и способа коррекции ещё нет. Наличие ID
и несколько свежих кадров не доказывают достижимость блока. Без измерений
действует отдельный таймаут. Автоматического вставания или отпускания уже
удерживаемой руки нет. `--ids 0 1` и `--demo-transfer` сохраняют интерфейс,
но пока останавливаются на первой цели: второй захват и перенос недоступны.
`--prepare-only`, `--approach-only` и наблюдение без `--execute` сохраняются.

Подсаживание выделено без изменения команд и длительности кадров:
`ActionGroups/clamp_left_crouch.d6a` содержит кадр 1 исходного `clamp_left`
(1000 мс), `ActionGroups/clamp_right_crouch.d6a` — кадры 1–2 исходного
`clamp_right` (1000 + 1000 мс). Исходные группы не изменены; последующие
кадры захвата не воспроизводятся. Пауза на измерение добавлена после этих кадров.
Оба новых файла нужно скопировать в каталог `--action-path`, по умолчанию
`/home/ubuntu/software/ainex_controller/ActionGroups/`; одного скрипта недостаточно.
Например, после задания SSH-адреса робота (на ноутбуке, из корня проекта):

```bash
scp robot/tag_grab.py robot/ActionGroups/clamp_left_crouch.d6a robot/ActionGroups/clamp_right_crouch.d6a "$ROBOT_SSH":/tmp/
ssh "$ROBOT_SSH" 'docker cp /tmp/tag_grab.py ainex:/home/ubuntu/robotrio/tag_grab.py'
ssh "$ROBOT_SSH" 'docker cp /tmp/clamp_left_crouch.d6a ainex:/home/ubuntu/software/ainex_controller/ActionGroups/clamp_left_crouch.d6a'
ssh "$ROBOT_SSH" 'docker cp /tmp/clamp_right_crouch.d6a ainex:/home/ubuntu/software/ainex_controller/ActionGroups/clamp_right_crouch.d6a'
```

Буфер кадров сбрасывается существующим `action()` после завершения приседа
и выдержки `--settle`. В журнал `POST_CROUCH_MEASUREMENT` записываются ID,
timestamp изображения и x/y каждого из `--stable-frames` свежих валидных
обнаружений. Этот параметр задаёт число образцов, а не стабильность позиции.
Измерения попадают в сообщение остановки, но не разрешают захват: геометрический
критерий пока отсутствует. Это сбор данных, а не TF-позиционирование или калибровка.
Новая последовательность с паузой в приседе на роботе ещё не проверена.

Для перехода на TF и коррекции после приседания не хватает подтверждённых данных:

- аппаратной цепочки от оптической камеры (`camera` в header) через подвижную
  голову к основанию и рукам; vendored URDF содержит только фиксированный
  `body_link → camera_link`, а монтаж в симуляции не является калибровкой робота;
- актуальных состояний головы/рук и трансформов на timestamp изображения после движения;
- геометрии `tag → block` и целевой точки/позы захвата каждой руки;
  для печатных меток ID 0–2 из PDF размер чёрного квадрата равен 0.028 м,
  но размер распечатки и настройки действующего детектора ещё нужно сверить;
- калибровки финальной позиции и способа коррекции из приседа: допустимой ошибки
  положения/ориентации блока относительно каждой руки и подтверждённых движений
  коррекции. Пороги подхода из стойки нельзя переносить туда автоматически.

Эти сведения могут быть доступны на роботе; его действующая TF-цепочка не проверялась.

## Видеопоток камеры через SSH

Для просмотра изображения нужен поток `/camera/image_rect_color` или
`/camera/image_raw`. `/camera/camera_info` содержит параметры калибровки,
а не видеокадры. Параметры печатных AprilTag из PDF приведены
в [справочнике](SERVOS_RU.md#id-apriltag).

В штатном `bringup.launch` предусмотрен `web_video_server`. Его стандартный
HTTP-порт — 8080; адрес ниже рассчитан на уже работающий сервер, доступный
на `127.0.0.1:8080` хоста робота. SSH-адрес `pi@192.168.149.1` взят из
[памятки запуска](../ainex_startup_checklists.pdf); при другой сети замените
его фактическим адресом. Порт и доступность сервера на роботе в этой сессии
не проверялись.

**На ноутбуке** откройте туннель и оставьте терминал работающим:

```bash
ssh -N -o ExitOnForwardFailure=yes -L 127.0.0.1:18080:127.0.0.1:8080 pi@192.168.149.1
```

После подключения откройте в браузере ноутбука:

- [Изображение с коррекцией дисторсии](http://127.0.0.1:18080/stream_viewer?topic=/camera/image_rect_color).
- [Исходное изображение камеры](http://127.0.0.1:18080/stream_viewer?topic=/camera/image_raw).
- [Список доступных потоков](http://127.0.0.1:18080/).

Прямая ссылка MJPEG для `/camera/image_rect_color`:
`http://127.0.0.1:18080/stream?topic=/camera/image_rect_color`.
Формат ссылок и стандартный порт сверены с
[исходниками web_video_server для ROS 1](https://github.com/RobotWebTools/web_video_server/blob/ros1/src/web_video_server.cpp).
Если изображения нет, проверьте список потоков и фактический порт сервера;
туннель сам не запускает камеру или ROS-узлы. Для закрытия туннеля нажмите
Ctrl+C в его терминале. Второй полный bringup ради просмотра не запускайте.

## 1. Скопировать файл

На ноутбуке из корня проекта:

```bash
read -r -p 'SSH-адрес робота user@IP: ' ROBOT_SSH
scp robot/line_follow.py "$ROBOT_SSH":/tmp/line_follow.py
ssh "$ROBOT_SSH"
```

На хосте робота, при работающем контейнере `ainex`:

```bash
docker exec ainex mkdir -p /home/ubuntu/robotrio
docker exec ainex bash -c 'if [ -f /home/ubuntu/robotrio/line_follow.py ]; then cp -p /home/ubuntu/robotrio/line_follow.py /home/ubuntu/robotrio/line_follow.py.backup; fi'
docker cp /tmp/line_follow.py ainex:/home/ubuntu/robotrio/line_follow.py
docker exec -it ainex bash
```

Настройки из `simulation/` копировать не нужно. Используются штатные `.d6a` робота: `forward_one_step`, `move_left`, `move_right`, `turn_left`, `turn_right`.

## 2. Подготовить окружение

Далее все команды выполняются **внутри `ainex`**:

```bash
source /opt/ros/noetic/setup.bash
source /home/ubuntu/ros_ws/devel/setup.bash
cd /home/ubuntu/robotrio
python3 -m py_compile line_follow.py
python3 line_follow.py --help
```

Драйверы и камера должны быть запущены штатным способом. Остановите другие сценарии движения. Проверьте изображение камеры: линия резкая и контрастная, корпус не закрывает рабочую область. Поза головы остаётся текущей.

## 3. Проверить распознавание без движения

```bash
python3 -u line_follow.py --max-seconds 30
```

Если камера публикует другой топик, укажите его:

```bash
python3 -u line_follow.py --image-topic /ваш/топик --max-seconds 30
```

Поиск идёт вплотную к нижнему краю: три соседние полосы от 80% до 100% высоты. Для изображения 640×480 это Y=384–479, общая высота 96 пикселей вместо прежних 120; по X сохраняется центральная половина кадра (160–480). Ближняя полоса задаёт боковое смещение, разность между дальней и ближней — направление линии. Положение головы не меняется. Границы задаются константой `ROIS` в начале скрипта.

В журнале видны смещение `offset`, наклон `heading` и выбранное действие. Зелёные прямоугольники показывают актуальные области поиска. В графической сессии можно открыть размеченное изображение:

```bash
rosrun rqt_image_view rqt_image_view /line_follow/image
```

На неподвижном роботе сместите линию физически вправо. Если `offset` положительный, ориентация — `standard`; если отрицательный — `mirrored`. Проверьте выбранную ориентацию, например:

```bash
python3 -u line_follow.py --image-orientation standard --max-seconds 30
```

Ожидаемые решения: линия по центру → `forward_one_step`, параллельно справа → `move_right`, слева → `move_left`; при наклоне — соответствующий поворот. Для надёжного решения линия должна быть видна минимум в двух рабочих областях. При потере линии движение не начинается.

## 4. Запустить движение

Сначала установите робота в устойчивую штатную стойку на полу, освободите руки и зону движения. Проверьте решения в наблюдении. В примерах ниже `standard` замените на фактически проверенную ориентацию.

Первый запуск — максимум одна ActionGroup:

```bash
python3 -u line_follow.py \
  --execute --empty-hands --image-orientation standard \
  --max-actions 1 --max-seconds 30
```

Оцените направление шага, равновесие и положение линии после движения. Затем можно ограничить серию:

```bash
python3 -u line_follow.py \
  --execute --empty-hands --image-orientation standard \
  --max-actions 10 --max-seconds 60
```

Непрерывное следование до остановки оператором:

```bash
python3 -u line_follow.py \
  --execute --empty-hands --image-orientation standard
```

**Остановка — Ctrl+C.** Уже отправленный кадр может завершиться; оператор должен иметь возможность поддержать и остановить робота. Скрипт не устанавливает начальную стойку автоматически и не измеряет физическую успешность шага.

## Основные параметры

| Параметр | По умолчанию | Назначение |
|---|---|---|
| `--image-topic` | `/camera/image_raw` | Топик `sensor_msgs/Image` |
| `--line-color` | `black` | `black` или `white` |
| `--threshold` | `80` | Порог яркости 0–255 |
| `--deadband` | `0.04` | Допустимое боковое смещение относительно ширины кадра |
| `--heading-deadband` | `15` | Допустимый наклон линии, градусы |
| `--max-actions` | `0` | Максимум ActionGroups; 0 — без ограничения |
| `--max-seconds` | `0` | Максимальное время; 0 — без ограничения |
| `--action-path` | Штатный каталог AiNex | Другой каталог `.d6a`, если нужен |

Настраивайте по одному параметру в режиме наблюдения. Алгоритм ещё не подтверждён на реальном роботе; последнее симуляционное испытание кривой линии выявило чрезмерный боковой уход. Полное прохождение кривой проверяется после единичных движений на прямой.

## Размещение куба одной рукой

`ActionGroups/place_block_left.d6a` и `ActionGroups/place_block_right.d6a`
получены из исходного `place_block.d6a`. Сохранены 24 кадра, порядок,
длительности (10,52 с), значения ног ID 1–12 и выбранной руки.
Кадры 1–2 — начальная поза и приседание, 3–12 — правая траектория,
13–22 — левая, 23–24 — подъём. Открытие правого захвата ID 22 происходит
в кадре 5, левого ID 21 — в кадре 15. Голова ID 23–24 не задействована.

| Группа | Выбранная рука, ID | Фиксированная противоположная рука, ID: значение |
| --- | --- | --- |
| `place_block_left` | 13, 15, 17, 19, 21 | 14: 165, 16: 170, 18: 520, 20: 930, 22: 570 |
| `place_block_right` | 14, 16, 18, 20, 22 | 13: 835, 15: 830, 17: 480, 19: 70, 21: 430 |

Невыбранная рука во всех кадрах получает абсолютную позу исходного кадра 1:
MotionManager отправляет все 22 значения, пропуска сервоприводов нет.
Произвольный текущий захват не сохраняется автоматически. Например,
`clamp_left` заканчивается на ID 21 = 400, здесь задаётся 430.
После левой группы ID 21/22 = 500/570, после правой — 430/500;
последовательный вызов может снова закрыть ранее открытый захват.

Скопируйте два новых файла в `/home/ubuntu/software/ainex_controller/ActionGroups/`
или каталог, указанный в `MotionManager(action_path=...)`.
Имена вызовов: `run_action('place_block_left')` и `run_action('place_block_right')`.
Исходный `place_block` и другие группы сохранены. Текущий `tag_grab.py`
останавливается после приседа и измерения, до захвата и размещения.
Штатные `left_hand_put_block`/`right_hand_put_block` содержат другие
10-кадровые траектории без приседания.

Источник: `simulation/artifacts/d6a_from_robot/home/ubuntu/software/ainex_controller/ActionGroups/place_block.d6a`,
SHA256 `902702310bc4784490098f8ee9f9c9c024f4e1bcef493dd2e605cde9f9fa4422`.
Формат и разделение проверены офлайн; новые группы физически и в симуляции
не испытывались.
