# Сервоприводы и идентификаторы AiNex

Справочник описывает все 24 сервопривода из конфигурации AiNex, отдельно
перечисляет используемые ID AprilTag и задаёт основу для обсуждения модуля
установки блока. Левая и правая стороны указаны относительно самого робота.

Первая задача модуля: робот уже удерживает один блок выбранной рукой,
определяет положение паза по AprilTag, позиционируется относительно паза
и устанавливает блок. Архитектура ниже предложена для согласования;
программная реализация этого сценария ещё не выполнена.

## Источники и достоверность

- [Документ о ходе разработки AiNex](../Hiwonder_AiNex_Ход_разработки.docx)
  задаёт общий цикл поиска, захвата, переноса и строительства. Для этой задачи
  в нём выбрано позиционирование по AprilTag вместо следования линии.
- [servo_controller.yaml](../simulation/vendor/ainex/src/ainex_driver/ainex_kinematics/config/servo_controller.yaml)
  задаёт соответствие `servo.id`, `joint_name` и калибровочного `init`.
- [Модель AiNex](../simulation/vendor/ainex/src/ainex_simulations/ainex_description/urdf/ainex.urdf.xacro)
  задаёт названия суставов и их связи.
- [MotionManager](../simulation/vendor/ainex/src/ainex_driver/ainex_kinematics/src/ainex_kinematics/motion_manager.py)
  определяет формат команд, чтение положений и исполнение ActionGroups.
- [Заполненный лист проверки](SERVO_CHECKLIST_RU.md) содержит результаты
  физической проверки пользователем: назначения, направления и исходные
  положения приводов. Дополнительные опорные положения приведены ниже.
- [tags.yaml](../simulation/vendor/ainex/src/ainex_example/config/tags.yaml),
  [settings.yaml](../simulation/vendor/ainex/src/ainex_example/config/settings.yaml)
  и [tag_grab.py](tag_grab.py) определяют известные настройки и роли меток.

Локальные исходники HiWonder находятся в игнорируемом каталоге
`simulation/vendor/ainex`. Их версия закреплена в
[vendor.lock](../simulation/vendor.lock):
`e8fe2a816797cf83054135160df5a82ec3596a69`.
Восстановление локальной копии описано в
[руководстве симуляции](../simulation/README.md#подготовка-перед-первым-запуском).
Исходный Word-документ хранится отдельно и пока не включён в Git.

Программные имена и `init` ниже взяты из исходников этой версии. Физические
назначения, направления и исходные положения сверены пользователем на роботе
и перенесены из чек-листа. Имена CAD для ID 17–20 не совпадают с бытовым
описанием движения: `*_el_pitch` вращает предплечье, `*_el_yaw` сгибает локоть.
Это не перестановка ID: положение осей в кинематической цепи соответствует
этим назначениям. Имена в конфигурации и коде не переименованы.
Полные механические пределы всех приводов пока не подтверждены.
Исходные ActionGroups с робота уже подтверждены пользователем и используются
через `MotionManager.run_action`.

## Полная карта сервоприводов

`init` — калибровочное значение pulse, соответствующее нулю сустава
в конфигурации. Это не команда начальной стойки и не измеренное положение.
Исходный pulse — фактическое чтение в начальной позе из чек-листа, не новая
калибровка и не команда движения. Направления переданы словами оператора;
для геометрического расчёта ещё нужны оси и нули физических углов.

### Группы ID

| Группа | ID | Количество |
| --- | --- | ---: |
| Левая нога | 1, 3, 5, 7, 9, 11 | 6 |
| Правая нога | 2, 4, 6, 8, 10, 12 | 6 |
| Левая рука с захватом | 13, 15, 17, 19, 21 | 5 |
| Правая рука с захватом | 14, 16, 18, 20, 22 | 5 |
| Голова | 23, 24 | 2 |

В конфигурации каждый из этих приводов использует `port_id: 1`.
ID 0 и 25–30 в таблице контроллеров сервоприводов не назначены.
Поле `max_motor_id: 30` описывает настройку порта и не означает наличие
30 сервоприводов.

В исходном списке `serial_ports.connected_ids` ID 12 указан дважды,
а ID 21 пропущен. Поэтому источником карты служат записи
`controllers.*.servo.id`, где представлены все ID 1–24 без повторов.
Этот справочник не изменяет исходную конфигурацию.

### Pulse и механические пределы

В `servo_controller.yaml` для ID 13 и 14 записаны `min: 1000`, `max: 0`,
для остальных — `min: 0`, `max: 1000`. Обратный порядок у плеч используется
программным преобразованием pulse в угол для задания знака. Эти поля
и протокольные значения 0–1000 не являются подтверждёнными механическими
пределами конкретного робота; пределы URDF также их не заменяют.

До новых прямых команд необходимы подтверждённые механические пределы
каждого затрагиваемого ID. Отдельно для каждого привода следует зафиксировать
минимальное и максимальное допустимое значение, направление движения
и источник подтверждения. Значение `init` само по себе таких сведений не даёт.
Для штатного вызова уже подтверждённых исходных ActionGroups повторная
проверка диапазонов не требуется.

| ID | Физическое назначение | Наблюдённые положения |
| ---: | --- | --- |
| 13 | Левое плечо, вперёд/назад | 725 — плечо параллельно телу |
| 14 | Правое плечо, вперёд/назад | 275 — плечо параллельно телу |
| 19 | Сгибание левого локтя | Примерный рабочий диапазон 60–300; 148 — прямой угол |
| 20 | Сгибание правого локтя | Примерный рабочий диапазон 700–940; 850 — прямой угол |
| 21 | Левый захват | 360 — открыто; 400 — достаточно для удержания проверенного груза |
| 22 | Правый захват | 650 — открыто; 610 — достаточно для удержания проверенного груза |

Рабочие диапазоны локтей указаны как примерные, а не как установленные
механические пределы. Положения удержания относятся к проверенному грузу;
его размеры и ширина раскрытия пока не записаны. Это не положения полного
закрытия без груза. Аппаратные `init`, рабочая конфигурация и ActionGroups
сохранены. Опорные положения и направления применены к модели отдельно,
как описано ниже.

### Привязка модели симуляции к физическим наблюдениям

В генераторе модели исправлены направления левого голеностопа ID 1,
правого плеча вперёд/назад ID 14, поворота левого предплечья ID 17
и поворота головы ID 23. Для ID 1 «левая сторона вниз» трактуется как
опускание левого края подошвы относительно самого робота. Существующая
коррекция боковых осей плеч ID 15–16 сохранена. Для остальных приводов
направления исходных осей согласуются с наблюдениями.

Отдельные нули pulse заданы в URDF атрибутом `robotrio_servo_init`:

| ID | Сустав модели | Ноль pulse только для модели | Основание |
| ---: | --- | ---: | --- |
| 13 | `l_sho_pitch` | 725 | Плечо параллельно телу в плоскости вперёд/назад |
| 14 | `r_sho_pitch` | 275 | Плечо параллельно телу в плоскости вперёд/назад |
| 19 | `l_el_yaw` | 523 | При 148 угол −90°: 148 + 375 pulse |
| 20 | `r_el_yaw` | 475 | При 850 угол +90°: 850 − 375 pulse |

375 pulse соответствуют 90° в используемом преобразовании 1000 pulse / 240°.
ID 17–18 продолжают управлять продольным поворотом предплечий, ID 19–20 —
поперечным сгибом локтей. Перестановка этих ID исказила бы кинематическую цепь.
Для захватов сохранены исходные нули и противоположные направления закрытия:
ID 21 закрывается при увеличении pulse, ID 22 — при уменьшении.
Ширина раскрытия и удержание реального груза по одной модели не подтверждены.

В свободной модели `stand` по-прежнему встраивается в начала суставов;
`robotrio_initial_angle` учитывает это смещение при командах и обратном чтении.
Показания начальной позы из чек-листа не заменяют команды исходного `stand`.
Примерные рабочие диапазоны локтей не превращены в механические пределы URDF.
Массы, контроллеры, физика и геометрия деталей не менялись; параметры камеры
и её монтаж всё ещё требуют аппаратной калибровки.

## ID AprilTag

ID метки и ID сервопривода принадлежат разным системам идентификаторов.
Например, AprilTag 1 не связан с сервоприводом 1.
Параметры печатных меток проверены по
[robotrio_apriltag36h11_35mm.pdf](../robotrio_apriltag36h11_35mm.pdf):

| Параметр | Значение в PDF |
| --- | --- |
| Семейство | `tag36h11` |
| ID и количество | 0, 1, 2; по три одинаковые копии каждого ID |
| Размер вырезанной метки с белым полем | 35 × 35 мм |
| Чёрный квадрат с кодом и чёрной рамкой | 28 × 28 мм |
| Белое поле | 3,5 мм с каждой стороны |
| Размер для оценки позы (`size` / `tag_size`) | **0.028 м**, без белого поля |
| Печать | A4, 100% / «Фактический размер», без подгонки |
| Контроль печати | Между крайними рисками линейки должно быть 100 мм |

Векторная геометрия PDF подтверждает чёрный квадрат 28 × 28 мм
(8 × 8 ячеек по 3,5 мм) и совпадение трёх копий в каждом столбце.
Фактический размер распечатки необходимо измерить линейкой: настройка
масштаба принтера может изменить размер. Бумажные 35 мм не подставляются
в `size` вместо 28 мм.

Ниже перечислены роли меток; ID метки паза пока не задан.

| ID метки | Где используется | Роль или состояние |
| ---: | --- | --- |
| 0 | PDF, `tag_grab.py` | В PDF — красный куб; в сценарии — цель для левой руки; в штатном `tags.yaml` отсутствует |
| 1 | PDF, `tag_grab.py`, штатный `tags.yaml` | В PDF — второй куб; в сценарии — цель для правой руки; штатный размер 0,1 м расходится с PDF |
| 2 | PDF, штатный `tags.yaml` | В PDF — третий куб; роль в сценарии не назначена; штатный размер 0,1 м расходится с PDF |
| 3 | Штатный `tags.yaml` | В PDF отсутствует; штатный размер 0,1 м; роль в сценарии не назначена |
| Требует назначения | Будущий модуль установки | Метка, по которой определяется положение паза |

Штатный `settings.yaml` выбирает нужное семейство `tag36h11`, но локальный
штатный `tags.yaml` содержит только ID 1–3 с `size: 0.1`. Для меток из этого
PDF ожидаются ID 0–2 с `size: 0.028`. Содержимое действующего детектора на
роботе в этой проверке не считывалось, конфигурация автоматически не менялась.
Определение ID 0 и размеры нужно сверить именно с загруженными настройками
детектора. ID 2 и 3 не следует автоматически назначать области строительства.

Видеопоток физической камеры через SSH и ссылки для браузера описаны
в [руководстве робота](README.md#видеопоток-камеры-через-ssh).

Для паза необходимо определить ID и размер метки, её положение и ориентацию
относительно паза, геометрию паза, целевую позу блока и допустимую ошибку.
Если метка закреплена рядом с пазом, её центр не совпадает автоматически
с точкой установки. Поза метки в камере должна преобразовываться в позу
паза с учётом этой привязки.

## Что уже есть для установки блока

В [руководстве робота](README.md#размещение-куба-одной-рукой) описаны
`place_block_left` и `place_block_right`. Их файлы находятся в
[ActionGroups](ActionGroups/); формат и исходные действия описаны в
[справочнике ActionGroups](../simulation/ACTION_GROUPS_RU.md).

Обе группы отправляют все ID 1–22: ноги, выбранную руку и фиксированную
позу противоположной руки. Голова ID 23–24 в них не участвует.
Следовательно, установка выбранной рукой не означает движение только
пяти её сервоприводов. Группы сохраняют траектории исходного `place_block`;
их пригодность для геометрии конкретного паза ещё нужно подтвердить.

Во время подхода штатные группы ходьбы также задают руки. Удержание блока
требует сохранения командной позы всех пяти приводов занятой руки,
а не только ID 21 или 22. Соответствующая логика уже есть в `tag_grab.py`,
но текущая последовательность останавливается с `CALIBRATION_REQUIRED`
после измерений в приседе. Она пока не реализует установку в паз.

`MotionManager.servo_position` хранит последние отправленные команды.
Это не измеренная поза и не подтверждение удержания блока.
Вызов `run_action` также не подтверждает физическую успешность установки.
Автоматический `stand` перед подходом требует отдельного решения:
эта группа задаёт обоим захватам 500 и может нарушить удержание.

## Предлагаемая архитектура первого модуля

Границы первой задачи: один уже удерживаемый блок, выбранная рука,
позиционирование по метке паза и установка. Поиск груза, новый захват,
следование линии, два блока и взаимодействие с другими роботами относятся
к последующим этапам общего сценария из исходного документа.

Предлагается отдельный сценарий `robot/place_block.py` в существующей среде
ROS 1 Noetic, без нового ROS-пакета и изменения драйверов. Внутри сценария
следует разделить четыре обязанности:

1. **Наблюдение.** Выбирать только нужный ID из `AprilTagDetectionArray`,
   проверять свежесть наблюдений и получать позу метки. Существующий
   `tag_grab.py` использует `/tag_detections`; фактическое имя топика
   остаётся настраиваемым. Сообщение детектора содержит `id`, `size`,
   `corners` и `pose`.
2. **Позиционирование.** Вычислять целевое положение относительно паза
   с учётом привязки метки и выбранной руки. Для пространственного расчёта
   нужны калибровка камеры, преобразования через подвижную голову
   и актуальные состояния на время изображения. Пока аппаратная цепочка
   не подтверждена, нельзя считать координаты камеры координатами руки.
3. **Движение.** Последовательно вызывать штатные ActionGroups через
   `MotionManager`, сохраняя удерживаемую руку при корректирующих шагах.
   При переходе к установке выбранная рука получает траекторию установки;
   допустимая поза второй руки должна быть определена заранее.
4. **Сценарий и результат.** Управлять переходами между наблюдением,
   выравниванием, установкой и проверкой, ограничивать время и число
   коррекций, различать окончание ActionGroup и подтверждённую установку.

Предлагаемая последовательность:

```text
ОЖИДАНИЕ МЕТКИ → ВЫРАВНИВАНИЕ → ГОТОВНОСТЬ К УСТАНОВКЕ
              → УСТАНОВКА → ПРОВЕРКА РЕЗУЛЬТАТА → ЗАВЕРШЕНИЕ
```

Готовность к установке должна учитывать ошибку положения и ориентации
относительно паза, согласованность свежих наблюдений и допустимую исходную
позу с блоком. Пиксельные пороги захвата из `tag_grab.py` для этого
не откалиброваны. После каждого корректирующего движения нужны новые
наблюдения; при потере цели до начала установки следующие корректирующие
движения прекращаются. Во время установки видимость метки может измениться:
политику остановки и восстановления нужно определить для выбранной траектории.
Автоматическое разжатие захвата или вставание при ошибке не предполагается.

Для первого интерфейса достаточно выбора руки, ID метки паза, топика,
каталога ActionGroups и явного `--execute`. Без `--execute` предлагается
показывать наблюдения и план без команд движения. Названия параметров
и структура реализации согласуются перед написанием кода.

### Данные для согласования задачи

До реализации необходимо определить:

- ID, физический размер и расположение AprilTag паза, его привязку к пазу;
- размеры блока и паза, высоту установки, ориентацию и глубину посадки;
- допустимую исходную позу руки с блоком и положение свободной руки;
- доступные на роботе данные позы, состояния суставов и преобразования;
- точность выравнивания и пригодность `place_block_left/right` для этого паза;
- наблюдаемый критерий успешной посадки, момент отпускания блока
  и поведение при потере метки или неудачной установке.

Первый проверяемый результат будущей реализации: при заданной руке
и метке паза робот выравнивается с удерживаемым блоком, выполняет
согласованную траекторию и сообщает результат согласно выбранному критерию.
Проверка геометрии в симуляции и физическое испытание на макете являются
отдельными этапами; в текущей сцене симуляции паз и AprilTag отсутствуют.
